**两条结论**：
1. 可见路径本身是通的：窗口不再被 `WA_DontShowOnScreen` 藏起来、不拦输入、退出干净。`desktop-lab/qt_host.py` 的可见开关是 `QY_LAB_VISIBLE=1`，默认不设，隐藏基线行为不变。
2. 同一套用例在私有桌面上给出与隐藏批次一致到 0.1ms 的 p95（83.4 / 66.6），说明这两个数不是噪声，是软件合成路径的稳定属性。所以 Q1、Q2 必须换到真实上屏的桌面上才能推翻或确认。

## 5. 已经确认的事实（决定了这趟怎么跑）

- **Qt 合成是产品自己选的软件路径**：`novelreader/qt_rendering.py` 在 Windows 上默认 `QT_QUICK_BACKEND=software`，只有 `QYREADER_RENDER_MODE=hardware` 才走硬件；文档写明加速的 Quick 合成会整帧丢失。所以 `graphicsApis=Software` 不是环境异常，是产品现状。
- **Chromium 的 GPU 在私有桌面上拿不到**：宿主 stderr 有 `Failed to create GLES3 context, fallback to GLES2` 与 `Failed to create shared context for virtualization`。私有桌面没上屏，这部分不能代表真实桌面，所以私有批次只作管线验证，不判阈值。
- **本机有独立显卡**：`AMD Radeon(TM) Graphics`，驱动 31.0.14051.1000；会话是 `console`（ID 1，运行中），不是远程桌面。也就是说上屏跑有机会拿到硬件光栅，这正是 Q1/Q2 要看的。
- **窗口会抢焦点**：可见模式下 `activateWindow` 仍是空操作，但窗口正常显示，点它就会获得焦点。自动通道期间不要接管鼠标键盘——`benchmark.mjs` 的悬停与滚动是页面内 CDP 事件，你一动真鼠标，悬停用例会打到自己窗口上。

## 6. 明确不做的事

- 不改产品代码、不改前端产物、不重建 `prototype/dist`。
- 不与隐藏批次做差值：`visible-accept.json` 里 `validForComparison` 固定 `false`，只用来判阈值，不并入那条软件合成的历史序列。
- 私有桌面批次不进验收结论，只作为"管线可用"的证据。

## 7. 已知局限

- `--desktop active` 不截图、不录屏，闪帧靠人眼；要客观证据得另加录屏，本轮没做。
- 自动通道 12 个用例里没有真播放，听感只在 `--hold --audio` 里。
- 可见窗口的 rAF 仍是渲染器调度口径，不等于显示呈现时间；它能回答"合成/栅格是否还压着 21ms 门槛"，但不能替代显示器端的实测。
